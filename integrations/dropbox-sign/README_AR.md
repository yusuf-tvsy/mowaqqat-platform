# تكامل Dropbox Sign مع كادر — نموذج آمن غير منشور

**الحالة:** وحدة ربط تجريبية جاهزة لاختبارات محلية؛ **ليست متصلة بإنتاج كادر ولا تستقبل أحداثًا حقيقية**.

## لماذا وحدة مستقلة؟

بوابة Render الحالية تمرر الطلبات إلى التطبيق الأصلي، بينما الشيفرة الداخلية للمكتب القانوني وواجهات حفظ العقود غير متاحة في هذا المستودع. لذلك لا يجوز افتراض وجود API للعقود أو إدخال سجلات مباشرة في قاعدة إنتاج كادر. الوحدة مستقلة ولا تغيّر البوابة أو البيانات الحالية.

## وظائفها

- تقبل Dropbox Sign callback عبر POST /hooks/dropbox-sign مع JSON، أو form-urlencoded، أو multipart/form-data.
- تتحقق من HMAC-SHA256 باستعمال event_time + event_type ومفتاح API الأساسي؛ وتقارن البصمات بشكل ثابت الزمن.
- تقبل فقط أحداث حالات التوقيع المحددة؛ وتتجاهل أنواع الأحداث الجديدة حتى تضاف وتختبر.
- ترسل إلى كادر: معرف الطلب، نوع الحدث، حالة الطلب، زمنه، ومفتاح idempotency؛ **دون محتوى العقود أو بيانات الموقعين**.
- لا تعيد تأكيد استلام الحدث إلا بعد نجاح استلامه من واجهة كادر. عند غياب الإعدادات أو فشل كادر، ترجع 502/503 ليعيد Dropbox Sign المحاولة.
- تتطلب Kader Sync URL عبر HTTPS ضمن نطاق kader.media ورمز صلاحية للخادم، ولا تتبع إعادة توجيه HTTP.
- تتيح GET /healthz للفحص، ولا تُظهر كلمات مرور أو أسرارًا في السجلات.

## شروط الربط التي ما زالت مطلوبة

1. اعتماد الجهة المؤسسية المالكة لحساب Dropbox Sign؛ **الحساب الشخصي الحالي غير معتمد تلقائيًا لعقود الصندوق**.
2. إنشاء Dropbox Sign API app وتوفير حساب مخوّل ومفتاحه الأساسي داخل مدير أسرار آمن. لا تُلصق المفتاح في المحادثة أو المستودع.
3. تطوير endpoint محمي داخل كادر على KADER_SIGN_SYNC_URL، يمكّن المسؤول القانوني فقط من رؤية حالة العقود وفق صلاحيات الشركات.
4. يطبّق endpoint كادر سجلًا غير قابل للتكرار باستخدام idempotency_key ويحتفظ بمصدر الحدث وتاريخ التحقق، ويمتنع عن إنشاء عقد مجهول الهوية.
5. اعتماد مطابقة signature_request_id مع سجل العقد الموجود مسبقًا في كادر، وليس الوثوق بأي معرّف وارد لإنشاء عقود جديدة.
6. مراجعة المتطلبات القانونية للتوقيعات الإلكترونية حسب كل اختصاص قضائي.
7. نشر الخدمة في بيئة تجريبية، ثم اختبار callback_test والأحداث الموقعة والحالات الخاطئة، ثم اختبار الاستعادة والمراقبة؛ لا تنشر قبل الاعتماد.

## تشغيل محلي واختبار

Requires Node.js 20+.

    node --test integrations/dropbox-sign/tests/bridge.test.mjs

لتشغيل الخدمة بعد إعداد الأسرار *في بيئة تجريبية*:

    node integrations/dropbox-sign/server.mjs

## عقد API المقترح مع كادر

POST https://kader.media/mowaqqat/api/integrations/dropbox-sign/events

Headers:
- Authorization: Bearer <server-managed-secret>
- Idempotency-Key: <sha256>

JSON example (synthetic only):

    {
      "schema_version": 1,
      "provider": "dropbox_sign",
      "signature_request_id": "example-signature-id",
      "event_type": "signature_request_all_signed",
      "occurred_at": "2026-11-17T00:00:00.000Z",
      "status": "completed",
      "idempotency_key": "<sha256>"
    }

هذه **مواصفة مقترحة**؛ غير مثبت أن نقطة النهاية موجودة حاليًا داخل كادر. لا تقبل أحداث الإنتاج قبل تنفيذها واختبارها.

## ملاحظة مالية

قد يتطلب الاستخدام المباشر لواجهة Dropbox Sign اشتراكًا أو موافقة تطبيق. الإصدار التجريبي test_mode يساعد في التحقق دون إرسال طلبات توقيع قانونية.
